# HHBA 匹配 V6：资格三态 + JD 条件组 + 求职意向与职责证据分离

**开发基线：** 2026-11-08 的 \`main\`，提交 \`8ed0cc4bb4011a5ca7a8182857cc9edd423c19a7\`。
**发布边界：** 此次独立开发分支先进行 GitHub Actions 和 Cloudflare Preview 验收；未经确认不合并主分支、不启用收费 DeepSeek API 服务。

## 1. 已有问题

旧资格函数只返回 eligible true/false。对于 5 年经验岗位，「简历有明确 2 年经历」和「简历没有足够可解析的经历」都会被删除，用户无法得知应补充什么。

旧职业方向识别把简历里直接出现的职业名称视作推荐目标，但没明确区分「希望转行成为产品经理」与「曾负责产品需求、项目管理」两种完全不同的信息。

招聘官网会使用「必须 A 和 B」「必须 A 或 B」「三项中至少掌握两项」等结构，不能把所有提到的技能都简单改写为必须掌握。

## 2. 本轮规则

- 新纯函数 \`assessJobQualification\`：
  - \`ELIGIBLE\`：可证明已满足**该条 JD 明确披露且能确定的硬条件**。不代表录用概率、职位实时开放或实际执照真伪。
  - \`NEEDS_INFORMATION\`：原简历没有证明一个或多个明确条件。用户补充并重新授权分析后才可能进入 Top10。
  - \`INELIGIBLE\`：已证实经验、学历低于具体官网要求，或工作地点不能确认位于中国大陆。
- 只对原招聘要求有明确证据的技能、资格证书设条件组：\`ALL_OF\`、\`ANY_OF\`、\`AT_LEAST\`。条件组必须包含原文证据。无法确定句法的内容保留原有普通技能标记，不用于强制淘汰。
- 岗位合并层输出 \`qualification_reviews\` 最多 5 条，且**不会混入 Top10**。反馈仅列安全可读的缺少字段与条件，不输出简历原文、证书号码或其他敏感内容。
- 求职意向 \`career_intents\` 与职责证据 \`demonstrated_roles\` 分离。原始自由文本职业方向也保留后向兼容，但意向匹配只产生较弱的职业关联分，推荐解释必须提醒是转向求职。
- 已有 \`evaluateJobEligibility\` 保持返回旧布尔契约，避免无关模块突然崩溃；新增正式三态评估接口负责用户可理解的结果。

## 3. 不能过度推断的部分

- 「简历没提某项技能」是**缺少证据**，不等于用户不会该技能；
- 「简历有证书名字」不等于证书原件、执业注册或执照范围已核实；
- 「简历写期望产品经理」不等于有产品经理工作经验；
- 仅具备部分技能而不满足其他明确硬条件的职位不予推荐；
- 如果招聘 JD 的语义复杂或字段冲突，宁愿继续标记待核验，不编造肯定资格。

## 4. 测试与上线门槛

自动化契约包含三态、缺少学历/年限/技能、已证明不符、中文 ALL_OF/ANY_OF/N-of-M、证书任选其一、跨专业转向、候选池保留待补充条目、界面显示。

在服务启用前仍需要：
1. 真实 JD 和授权脱敏简历的人工标注集合（至少跨专业、毕业生与社招多个样本）。
2. API、Cloudflare 预览、隐私授权、返回编辑、成本和响应时延验收。
3. 正式站 DeepSeek 服务端凭据与额度保护（由用户在安全控制台配置，绝不放进聊天/PR）。
4. 通过后先低流量灰度；此 PR 不修改 Production 环境开关。
