# HHBA 第 07 模块｜双评分规则、动态重算与不可变历史

**状态：独立开发分支。具有真实 PostgreSQL 业务逻辑及测试，但生产认证/员工关系验证和申诉机制尚未接通；公众与企业评分强制保持待评估。**

## 使命与边界
企业每次改善员工待遇，都有机会通过独立核验后提高表现；真实优秀雇主会在后续审批机制建立后吸引人才并申请 HHBA 业务帮扶。但**不能让评价变成刷分、花钱买分或仅凭单方自述就改变企业命运的系统**。

## 已落地模块
- `apps/api/scoring_domain.py`：纯函数规则 `hhba-employer-v0.1-draft`，双百分制，缺少资料显示 pending/None 而非零分。
- `apps/api/scoring_store.py`：只读取当前已 verified 且安全扫描 clean 的独立评估证据，候选值由另外一名授权评分审核员评估 0—100 并写至少 25 字的审核依据；不能与材料提交人/文件初审人是同一人。评分计算只使用评分审核员的不可编辑意见，不能只看上传文件是否已核验。
- `infra/migrations/20261025_employer_scoring.sql`：内部证据评分、版本化候选快照；单份证据禁止原地改分，纠错需新证据与评估。结果输入指纹去重、历史不可直接 UPDATE/DELETE。
- `apps/api/scoring_routes.py`：独立评分审核员内部接口 + **始终返回待评估** 的公开接口。只有传入真实服务器会话验证和独立组织认证状态查询器才能注册路由；目前不挂到 healthz 骨架。
- `apps/web/src/pages/EmployerScoringPage.tsx`：透明规则页与管理员内部评分复核页。在 GitHub Pages 预览里不接收真实审批，不发布模拟分数。

## 当前规则：需要全部类别证据（权重为候选草案，不是最终官方评分体系）
信誉值（100%）：招聘信息诚信 50%、经营/履约诚信 50%。前提：企业认证为已通过且两类都有一年内独立评估的当前有效证据。

员工善待值（100%）：工资与劳动合同 20%、社会保障 20%、工时休假 15%、员工发展 15%、上一完整季度员工体验 30%。前提：企业认证通过、四项独立评估均可信、一年内有效，且员工反馈已满足模块06的至少十份真实反馈与季度结束才能公开的汇总门槛。

每个材料类别必须有经独立审核员明确评分的证据；无证据即 pending，**不能用其他类别高分填补缺失项**。新近证据若失效/存在争议，不复活同类旧高分。严格封顶员工反馈权重 30%，并不把员工主观分数等同于违法违规事实。

> 明确区分「核验文件存在」「文件内容独立审核」「真实用工合规事实」三种不同证据等级。真正生产版须设计正式评分核查手册与可验证的合规事实指标，目前 0—100 的审核评估是试验性候选值，不应被用户当作正式企业优劣评级。

## 动态更新机制
- 新资料经审核完成 → 单独创建 rubric finding，不修改旧 finding。
- 独立审核人员点击重算 → 检索最新每类 finding、重新读取当前证据有效状态、读取上一已结束季度安全汇总 → 计算内部 candidate。
- 相同输入（规则版本、认证、证据评估与状态变动、季度匿名汇总）生成相同指纹，不重复生成快照。
- 争议证据或过期资料导致失去覆盖时，重算相应一项变回「待评估」。旧快照仅用于内部审计，不可继续公开。
- 原始员工身份、票据、原始评分、时间、评论等**不进入候选快照**。
- 暂不做自动化事件触发重算、频率限制、事件订阅。这需要确保源状态更新事务与候选快照之间不会出现过时状态；正式发布前须解决。

## 禁止事项
1. **绝不开放真实公开数字**：模块 08 独立申诉、误判纠错、审核公开/撤销、评分规则批准之前，`public_score_guard()` 必须始终返回 pending/None。
2. `VITE_HHBA_SCORING_API_ENABLED=0`，没有可信后端权限时不能开启。证据核验 `VITE_HHBA_EVIDENCE_API_ENABLED` 和员工反馈 `VITE_HHBA_EMPLOYEE_FEEDBACK_API_ENABLED` 独立受控。
3. 不接 Railway 当前 ATS 阅读服务，不直接修改真实企业、员工隐私或原招聘数据。
4. 企业无权查看单个员工评分及任何可用于推测员工身份的分组、查询时间或实时计数。
5. HHBA 帮扶仍需要单独客户交付能力审核，内部候选评分**不能自动授予帮扶资格**。
