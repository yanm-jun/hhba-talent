# HHBA Phase 5 — 求职者主动申请与企业处理闭环

本阶段使用 **企业自行发布且经平台审核的 HHBA 企业直发岗位**。Greenhouse、Ashby、Lever 海外 ATS 岗位继续跳转企业官方投递系统，不能伪称 HHBA 代投递。

## 用户流程

1. 企业主体、经办人分别核验，招聘授权与平台门禁均有效。企业职位经管理员独立审核，仍在有效期内。
2. 求职者需要登录，并将个人能力档案核对为 `confirmed` 或 `published`。
3. 求职者打开企业直发岗位详情，点击**预览将向该企业分享的字段**；后端从经确认的个人档案重新生成允许展示的白名单字段。
4. 界面显示共享信息（仅姓名展示、职业方向、最多 8 项技能、地区、工作年限）。不提交整个档案、履历附件、解析证据、电话号码、邮箱或精确住址。简短申请说明也须做联系方式/精确住址过滤。
5. 求职者勾选**本岗位本次单独授权**并提交；授权完全独立于 `enterprise_search` 搜索授权，提交岗位申请不会改变搜索授权。
6. 企业登录后仅能查看自己认证组织当前有效公开岗位收到的申请。状态有限转换：已提交 → 审阅/入围/未通过；审阅 → 入围/面试/未通过；入围 → 面试/未通过；面试 → 企业标记录用/未通过。任何状态更新需经 CSRF 和并发状态检查。
7. 求职者可在“我的申请”查看状态，随时撤回申请。撤回后当前申请的分享快照与说明清空，企业检索该岗位的申请列表立即不再包含它。避免历史缓存继续展示须在运营环境关闭相关 API 公共缓存；数据库备份与审计留存另需明确合规保留政策。
8. 同一求职者对同一职位只允许一次投递，撤回后不支持同岗位重投，防止频繁骚扰。此限制在申请确认之前须告知用户。

## 上线门槛

- 后端 `apps/api` 与 PostgreSQL 当前**未作为此 GitHub Pages 预览的公网身份服务上线**，所以站内申请、进度与企业处理页均是**只读界面预览**。不可通过前端 API 模拟伪造录用或投递成功。
- DBA 在独立审核、备份与演练后执行 `20261020_phase5_job_applications` Alembic 迁移；不得在招聘同步/翻译生产服务上盲目修改数据。
- 使用同站身份会话、CSRF 防护、精确 CORS、安全 Cookie、速率限制、独立管理员核验、最小权限授权，以及 TLS 和数据库加密存储。GitHub Pages 和独立 Railway 域名并非同站，直接配置独立 API URL 不能保证登录可用。
- 告知申请人的个人信息处理目的、接收企业、保存时间和撤回机制；发布与备案合规文本。资料撤回后对当前表行清空，不应宣称已经从所有异地备份中永久删除。
- 企业联系求职者的站内消息、面试邀请和入职材料**不在本阶段自动实现**，招聘进度只表示企业在 HHBA 中记录的状态，不保证真实录用。
- 只读源码测试、浏览器模拟与带模拟用户的后端测试通过后，再由具备权限的管理员安排部署与真实端到端验收。

## 自动化验收

- `hhba-phase5-applications-ci.yml`：用合成招聘主体及求职者测试 CSRF、逐岗位授权、重复投递、禁止未经确认档案、跨企业隔离、不可随意跳级的招聘状态、撤回后快照清空、撤销招聘权限。
- `hhba-phase5-applications-browser.yml`：用手机 Chromium 检查静态 Pages 新入口与企业处理面板，确认后端未上线时没有虚构候选人、招聘记录或数据写入。
