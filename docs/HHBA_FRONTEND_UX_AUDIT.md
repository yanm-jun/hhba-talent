# HHBA Frontend UX V1 审查报告

日期：2026-10-14；分支：`feat/frontend-ux-v1`。

## 审查证据与范围

- 源码：`apps/web/src` 全量页面、路由、API Client、全局样式；API 路由以 `apps/api/app/main.py` 为准核对。
- 运行地址：Web `http://127.0.0.1:3003`，API `http://127.0.0.1:8003`（检查时均为监听状态）。
- 浏览器：Codex In-app Browser；首页桌面、求职端桌面、首页 390×844、企业端 390×844 已实测。截图由浏览器工具在本轮运行中采集并显示；该工具未提供安全的本地二进制落盘接口，因此没有伪造“截图文件路径”。

## 原版关键问题

| 优先级 | 页面/流程 | 发现 | 风险 |
|---|---|---|---|
| P0 | 求职端登录前选文件 | 跳转登录后仅保留路由，`File` 对象丢失 | 用户必须重新选择私密简历 |
| P0 | 解析页 | `uploaded/queued/parsed` 等内部状态与“开始本地解析”交给用户理解 | 用户不清楚下一步，刷新后无法回到任务 |
| P0 | 名片 | 仅展示 `public_share` 单一复选框，已存在的三项独立授权没有可见管理入口 | 授权边界不透明 |
| P1 | 资料核对 | 一进入即是少量字段表单，没有先解释已提取的信息与待补充内容 | 价值反馈晚、填写负担高 |
| P1 | 企业端 | 标题和描述与组织创建混在同一页；“告诉 AI”容易造成已进行大模型推理的误解 | 登录和组织步骤打断输入，造成误导 |
| P1 | 首页 | 有开发演示文案“HHBA 首页目标结构示意” | 不应出现在正式界面 |
| P2 | 全站 | 标题仍为“环境就绪检查”；加载/错误/空状态不一致 | 产品完成感不足 |

## 原流程与改进后流程

### 首次求职者

原流程：首页 → 求职页 → 选择文件 → 登录（文件丢失）→ 再选文件 → 上传 → 手动开始解析 → 长表单。

新流程：首页 → 求职页 → 选择文件 → 登录（同一次 SPA 会话中保留文件，不上传）→ 上传并自动安排整理 → 三阶段状态 → 摘要核对 → 分组编辑 → 私密名片 → 独立授权/发布。

重复选文件的必需次数从 2 次降至 1 次；手动“开始解析”步骤取消。

### 首次企业 HR

原流程：进入企业页即见标题、需求、组织和草稿管理；未登录时保存才知道会跳转。

新流程：自然语言需求输入 → “需求整理”核对页（仅保留原文与待确认项）→ 登录/注册 → 创建或选择组织 → 保存私密草稿 → 需求列表恢复。

## 前后端衔接审查

现有 API 已有安全上传、解析队列、档案确认/发布/撤回、组织隔离和需求草稿能力。为支持前端恢复而增加两个只读、已认证接口：

- `GET /api/v1/me/resumes`：仅列出当前用户自己的简历及任务概况；用于恢复未完成处理。
- `GET /api/v1/me/consents`：返回三项已有授权的布尔状态；默认均为 `false`。

`GET /me/profile` 额外返回已有字段 `display_name`，方便名片预览。不改变权限、迁移、Worker 或公开资料白名单。

## 遗留审查项

当前端口 8003 的 API 是未开启热重载的既有进程，未加载本轮新只读接口。因此发布前需重启**仅 HHBA API**，再完成认证后的浏览器回归。此项不代表代码或安全测试失败，但使本轮“全浏览器闭环”证据尚未完整。
