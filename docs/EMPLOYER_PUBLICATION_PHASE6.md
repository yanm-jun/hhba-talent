# HHBA 企业成长模块 10｜公开双评分、版本化发布与撤销治理

**状态：独立分支 + 独立 PostgreSQL 测试 + GitHub Pages 静态预览。生产发布默认关闭。**

## 目标与边界
企业信誉值与员工善待值不应只是一对漂亮数字。只有基于完整核验证据、受保护的员工季度反馈、争议已经解决、评分规则经独立政策批准、发布审核员互相回避，才可能公开。员工、求职者、企业看到同一份获准公开的评分，不能购买或擅自更改。未公布的是「待评估」，**不是零分**。

## 模块组成
- `infra/migrations/20261025_employer_publication.sql`：私有发布候选、首次审核、第二次审核、拒绝、撤销、企业版本号，附只追加事件审计和数据库唯一有效发布约束。
- `apps/api/publication_domain.py`：得分完整性、经批准规则版本验证、审核利益冲突与隐私脱敏公开投影。
- `apps/api/publication_store.py`：仅从最近有效的内部评分快照发起发布；经不同的独立审核员两次签批后才发布；与真实证据、身份核验、员工季度隐私门槛、申诉状态动态联动。
- `apps/api/publication_routes.py`：公众档案、历史发布列表；受控的发布准备/审核/撤销接口。路由不自动挂进只有健康检查的 app；构造时 `policy_enabled=False`，且规则批准名单默认为空时拒绝发布。
- `apps/web/src/pages/EmployerVerifiedProfilePage.tsx`：公开双评分/真实改善/版本历史、内部发布治理后台。静态站 feature flag 关闭，不显示虚构分数、改善或订单；前端不能伪造审核权限。

## 强制发布条件
1. 企业认证实时有效。
2. 评分规则版本在后端独立批准的 allowlist 中；试点权重本身**不**自动构成正式审批。没有正式治理批准不得把 `hhba-employer-v0.1-draft` 加入生产 allowlist。
3. 最近一个完整季度的员工反馈满足至少 10 条独立核验的受保护汇总条件。不公开单条、人数变动、员工 ID 或提交时间。
4. 六类证据全部来源于同一企业的已核验、已完成安全扫描且一年内有效的材料，具有独立评估意见。评分使用最新且仍然有效的来源，后续新增审核/修改状态导致原版本不再可信时暂停展示。
5. 企业/员工隐私的活跃申诉、补充资料中或待纠正状态都阻止发布。争议发生后公开 API **立即 fail closed**。
6. 发布流程依次：独立准备人 → 第一独立签批人 → 第二独立签批人。所有参与者须与企业、资料提交者、原证据审核人、评分人、计算人回避；同一人无法签两次。
7. 任何组织最多一个有效公开分数版本，旧版需正式撤销后才可发布新版。撤销须由非原三人的独立复核者说明原因并留痕。
8. 历史公开记录仅展示获准发布的版本号、日期和是否被撤销；不泄露已撤销的旧分数或原始敏感评估。始终 `Cache-Control: no-store`。

## 不等于完成生产
- 本仓库 `apps/api/main.py` 仍只有 `/healthz`；须先核实真正在运行的统一账户、企业认证、成员与管理员角色、CSRF，以及员工在职核验与文件安全扫描后，才能接生产 API。
- 本次没有完成监管层面正式发布评分规则的批准、人工仲裁/申诉纠正结案制度、风险审计、法规评估、完整数据保留及公开纠错通知机制。正式站不会因此直接上线数字。
- 第 09 模块改善记录独立审核，只把当前有效且获准公开的事实显示在统一档案；不能推断分数提升、销量或客户订单。
- `VITE_HHBA_PUBLICATION_API_ENABLED=0` 且后端 `policy_enabled=False`，在上述外部合规与技术条件完成前不能开启。CI 的批准权重和独立 reviewer 仅为隔离测试的虚构身份，不是正式获批。
- 本模块**不**给企业自动授予 HHBA 帮扶资格，客服引荐和成交成果分别需要后续模块。
