# HHBA V8 第二阶段 — DeepSeek 全网公开招聘检索（不依赖企业私有 API）

日期：2026-11-08。用户明确要求以 **DeepSeek 自主搜索公开互联网** 为核心，不能以逐家企业开通 API 或适配国外 ATS 为前提。企业范围无限制；实际工作地点 **必须在中国大陆**，外资在中国大陆岗位亦可。

## 已验证的官方 API 能力（请勿混淆）

- DeepSeek **Search**：`POST /v1/tools/search`，使用企业公开网络索引查找 URL，无需向各招聘企业申请 API Key。
- DeepSeek **Fetch**：`POST /v1/tools/fetch`，读取公开网页的 Markdown，受到站点登录、政策和正文可访问性限制。
- DeepSeek V4 Pro **Responses**：`POST /responses`，允许模型动态决定搜索的关键词、读取哪些页面及何时核验，使用 `function` 工具调用；官方注明 `max_tool_calls` 会被忽略，因此不启用无法控费的内置 `web_search`。
- 资料：https://api-docs.deepseek.com/zh-cn/guides/search/ ；https://api-docs.deepseek.com/zh-cn/guides/responses_api/ 。

## 实现架构

代码：`apps/web/functions/_lib/deepseek-official-job-agent.js`。

1. 只向联网模型发送脱敏后的 **目标职业**，绝不发送手机号、邮箱、姓名或简历正文；现有 AI 简历理解仍走用户授权单独流程。
2. 模型决定搜索词；`search_jobs` 通过 DeepSeek Search 返回公开网页链接（不是企业招聘 API）。不在代码中维护固定的公司域名名单。
3. `read_job` 只能读取 Search 结果实际出现过的 HTTPS **单个岗位详情**。公开招聘聚合平台、社交媒体、普通职位列表、非 job URL、访问限制、没有岗位要求或无中国大陆办公城市的页面都不当作可推荐岗位。
4. `verify_employer` 查找 Search 搜出的另一独立公司网站页面，再通过公司名及公司域名一致性，或官网指向异域岗位网站的明确链接，交叉验证来源。仅通过搜索摘要、AI 单方声称“官网”、或单个职位页面都不能进入正式 Top10。
5. 只有有任职要求、独立公司网站佐证、准确大陆工作城市、申请入口证据和 Fetch 的时间戳才转 `OFFICIAL_DETAIL_FETCHED`，复用 V7 的已审计资格与融合排序。
6. **注意真实性边界**：公司名称和同注册域名相互印证只能证明公开网站之间存在一致性或链接关系，**不等于工商注册认证**；公开职位页面存在也不保证实时接收申请。前端仍显示需要到官网确认。

## 服务端硬限制

每次 **最多 4 次 Responses / 8 次 Search / 20 次 Fetch**；一旦达到请求的已核验岗位数量就提前结束，不要求耗尽预算。按用户每日 Search 限额及原有 AI 用户/全站每日配额执行。由于 DeepSeek 忽略 `max_tool_calls`，本实现没有开放内置服务端 web_search，而是由 HHBA 服务端执行每一个付费 Search/Fetch，并拒绝模型额外请求。

开关 `HHBA_MATCH_V8_DEEPSEEK_AGENT_ENABLED=1` 且现有 Preview `HHBA_MATCH_SERVICE_ENABLED=1`、`HHBA_MATCH_EXTERNAL_SEARCH_ENABLED=1` 才可能走此路径。正式站两个主开关继续关闭，V8 标志缺省关闭。

## 测试要求与评价指标

合约测试 `apps/web/scripts/match-v8-deepseek-agent.contract.test.mjs`：任意未预设企业招聘 URL、不同国内企业的公开网页、工作地点、任职要求、官网关联性、非官网/聚合页、伪造域名、境外职位、调用预算、Provider 错误、最终候选人资格融合。

下一项不是无条件上线，而是在受控 Preview 对**不含真实个人身份的职业搜索目标**执行小规模 V4 Pro + Search/Fetch 真实测试，记录搜索/抓取次数、职位详情确认数、最终合格推荐数、费用和时间。实测之前不能宣称达到“全中国覆盖”或者“搜索到即仍招聘”。

## 2026-11-08 下一阶段：国内官网职位正文解析与独立官网自动复核

在真实测试出现 12 条候选链接、4 个可读取页面但 0 条完整核验后，优先整改**站外页面的结构识别**，不是增加固定企业或私有 API。

- 从原来的固定标签匹配升级成**有界 Markdown 行分析**：`岗位名称`、`职位名称`、页面标题、Markdown 表格、标签与城市分行、职位名称位于首段的情况均可提取。

## V8 第四阶段：Search 证据优先、分企业读取（2026-11-08）

**问题依据**：前三次真实联网试验都找到招聘候选链接但通过官网职位核验为零；第三次 9 个读取页面中 7 个缺少工作地点，1 个缺少申请入口。继续增加 Fetch 不足以提高质量，必须先提高读哪一页的准确性。

**已实施（分支预览，不启用正式站）**：
- 深度使用 DeepSeek Search 官方响应中已有的 `title`、`snippet`、`summary`、`rerank_score`、`authority`、`date`，作为对**搜索候选 URL 的排序信号**：职业是否在标题、摘要是否包含工作城市、任职资格、职责和投递入口；标题为招聘列表、公告、岗位汇总、求职攻略等下降处理。
- 排序分数只影响**先读哪个链接**；摘要、发布时间、Search 权威性评分全部不能证明岗位真实性、工作地点或目前开放投递，任何一项都不得直接写入正式招聘资格结果。
- DeepSeek 的工具结果返回有限的候选证据提示（布尔值而非源网页原文），辅助模型优先选择具体详情；正式职位内容仍必须由独立 Fetch 获取。
- 搜索意图强化“具体职位详情 / 工作地点 / 任职要求 / 官方投递入口”，但不固定企业名单、不要求企业私有 API，也不强制一次查询堆砌所有关键词。
- 当模型的 4 次响应使用完，服务端只针对**搜索已返回的岗位 URL**最多补读 6 条。通过岗位相关性与以上证据线索排序，优先不同公司的岗位，每家公司首轮最多 2 条，避免某家公司占满 6 次 Fetch；仍受单次最多 20 次 Fetch 上限。
- 记录有限的 Search 元数据质量统计：候选链接数、有工作城市/任职资格/申请入口提示的候选链接数；不把用户个人简历或抓取的网页摘要写入 D1，不新增企业域名白名单。

**新增测试**：`apps/web/scripts/match-v8-search-quality.contract.test.mjs` 包含证据优先排序、列表页降权、公司多样性、Search 摘要不构成岗位证明、模型不用额外 API 调用即可优先读取有证据详情，及维持 4/8/20 预算。仍需通过 GitHub CI，必要时以无个人资料的真实搜索对照判定收益。

**上线门槛未改变**：真实官网 JD、独立企业来源证据、申请入口及中国大陆工作城市，学历经验资格三态硬筛选仍不可跳过；`main` 与 `hhba.work` AI 开关保持不变。

## V8 第五阶段：企业招聘主体的独立公开证据（2026-11-08）

**问题**：第四轮真实 V4 Pro/Search/Fetch 发现 27 条候选链接，完整读取 1 条岗位正文，但该条无法取得符合要求的企业官网关联证据；因此 Top10 仍为 0 条。禁止因为网站标题含公司名就放松跨域真实性核验。

本阶段针对代码 `apps/web/functions/_lib/deepseek-official-job-agent.js` 实现以下逻辑：

1. **同注册域企业主页**：候选 JD 读取成功后，先 Fetch 已搜索到的同注册域企业官方介绍/招聘页，若没有则尝试该注册域主页；要求独立页面与职位正文的招聘主体名称可交叉核对。
2. **企业招聘官网补救搜索**：前一途径不足且岗位正文明确写有招聘企业时，HHBA 以经过严格字符与注入词过滤的公开企业名生成“官方网站 社会招聘”搜索词。最多 **2 次企业查证 Search/一次匹配操作**，同时计入全局最多 8 次 Search；仅向 DeepSeek 发送岗位网页已公开的企业名，不发送用户简历、手机号或身份数据。
3. **跨域招聘入口证明**：企业官网必须公开链接到该职位的**精确 HTTPS 岗位地址**，或具有明确企业路径标识的招聘板 URL（例如 `/companies/<employer>`），并且该路径确实是职位 URL 的严格前缀。官网只链接到第三方招聘系统首页（如 `/jobs`）或其他企业招聘板，不能放行。
4. 公司主体、同域页面和申请入口证据均不能被 Search 摘要、模型自行声称、公司名称相似或单一站外招聘页面替代。无法证明时输出有限的失败分类，不入 Top10。
5. 公司官网补充读取每个待核岗位最多优先 2 页（已有 Search 页面/主页）+ 企业 Search 建议最多 2 页；所有读取计入单次 20 次 Fetch 硬上限，重复网址在本次操作内复用。模型仍最多 4 次、Search 最多 8 次、Fetch 最多 20 次，按真实 Token 和成功 Search/Fetch 次数记录费用。
6. 尽量覆盖国内自建官网及公开跨域招聘网站，不新增对 Ashby/Greenhouse/Lever 等国外 ATS 的特殊依赖，也不要求招聘企业开放私有 API。

测试：`apps/web/scripts/match-v8-employer-evidence.contract.test.mjs` 包括企业名注入防护、跨域精确职位、带公司身份的招聘板链接、拒绝第三方根域/跨企业链接、缺失企业官网时限额自主 Search+Fetch、预算与成本统计。只有所有 CI 通过，才允许进行下一次受控真实 API 质量对照。

**限制**：网页品牌和官方链接关系仍不等于政府工商注册认证、网页存在也不等于当前仍在招聘。生产 `main` 和 `hhba.work` AI 开关保持关闭。

## 第六轮真实联网及重大防假阳性整改（2026-11-08）

真实 OIDC 一次性测试：https://github.com/yanm-jun/hhba-talent/actions/runs/42489359554

- 仅用模拟“内容运营”，模型 4 / Search 2 / Fetch 13（Search 有内容 2、Fetch 有内容 9），发现 12 个候选链接、2 条通过程序正文结构解析。1 条曾被旧核验程序标为 `VERIFIED_JOBS_FOUND`，**人工复核发现是危险的假阳性，实际可信官方职位通过数应当记为 0**。
- 假阳性案例：`https://www.lbzhipin.com/jobs/220921.html`，程序报告 `company="全国 [切换]"`、`location="洛阳"`，并错误给出 `CORPORATE_DOMAIN_AND_BRAND`。这实际上是招聘信息平台导航文案，并非真实招聘企业；**不得进入真实 Top 10**。保留该公开链接只用于本轮验证缺陷，不以此证明职位仍开放。
- 原因：旧版在职位页没有企业名时，把同域招聘站点的首页标题当成雇主名称，又因为岗位页出现相同导航文字而错误交叉核验。仅凭同注册域、站点标题或出现在主页的某个企业名称，都不能证明平台就是用人单位。
- 修复：主页自动提取企业名必须有可辨认的实体名称（例如“有限公司/集团”等），拒绝“全国［切换］”“职位搜索”“招聘平台”“找工作”等导航/站点目录称呼。即使职位页写明某企业名称，仍要求公司独立主页**标题或开头自我介绍**直接标明该企业身份，不能只从招聘平台正文中的第三方企业列表提取名字；通用招聘平台页头须明确拒绝。
- 反例测试加入 `match-v8-employer-evidence.contract.test.mjs`，复现同域站点和明确公司名两种风险，保证假招聘主体不能通过；合法企业官网仍受支持。
- 实际 usage：输入 6,876 Token（缓存命中 5,376）、输出 470 Token；公开价工具估算 ¥0.055、模型 ¥0.013901，合计 **¥0.068901**，服务返回 `complete=false`，不视为最终账单。
- 失败统计：`MISSING_EXPLICIT_WORKPLACE=5`、`MISSING_DUTIES=1`、`POSTPASS_FETCH_UNAVAILABLE=3`、`COMPANY_PAGE_UNREADABLE=1`。原测试接口报告 1 条“核验通过”，但**经防假阳性检查应计为 0 条可信招聘职位**；不得拿原报告宣传搜索成功率。
- 本轮结束后删除 `v8-workplace-eval.js` 和对应 GitHub 工作流，清除 Preview D1 一次性测试锁，保留匿名数字费用记录，并待 Cloudflare 清理版本上线后删除旧的受保护测试部署。
