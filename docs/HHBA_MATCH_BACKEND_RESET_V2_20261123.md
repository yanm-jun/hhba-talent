# HHBA 智能岗位匹配后台重建（2026-11-23）

## 范围与目标

旧的“简历→多个 Agent / 原生 DeepSeek 联网 / ATS / 历史检查点 / 多层过滤”后台已造成反复出现 0 岗位、上游错误被掩盖、难以追查来源丢失。按照产品方要求，**停止旧匹配后台，开发独立 V2 后端**。

只重建**岗位智能匹配后台**，不重建或删除：账号和登录、私有简历库、文档 OCR、Word 简历编辑器、岗位匹配历史、其他网站服务、财务数据、R2/D1 共享存储。

## 旧链路处理

- `/api/match-native`：生产分支停止运行旧职位搜索，状态端点返回已停用，其他请求返回 410；仅历史代码/原有测试保留用于回退与逐步移除。
- 新前端不再调用 `/api/match-native`，统一使用 `/api/match-next`；“常规／原生试用”两套搜索选项从页面移除。
- 不删除历史数据库表、已保存的用户简历、用户历史结果，避免破坏个人数据。停用旧引擎和清空用户数据是两回事。

## Clean Match V2

1. 读取**已脱敏**的简历正文，使用既有稳定的简历证据识别组件。
2. 模型规划职业方向，结合**明确写明**的意向城市，扩展临近城市和全国其他机会。
3. 独立 DeepSeek Search API：按不同职位／城市查找企业官方具体职位 URL；模型不能自造链接。
4. 独立 DeepSeek Fetch API：真实打开职位页面。搜索摘要本身**不等于岗位正文**。
5. 原文验证企业、职位、工作地点、职责及任职要求；无明确大陆工作地点则不展示。
6. 模型对照网页 JD 与简历片段 ID 评分，证据不足时分数为空；不把匹配分当录用概率。
7. 每次报告搜索数量、来源数量、实际打开的网页、真实城市、具备证据的岗位及错误阶段。

技术入口：`apps/web/functions/api/match-next/[[path]].js`  
唯一新搜索引擎：`apps/web/functions/_lib/clean-match-v2.js`  
端到端合约测试：`apps/web/scripts/clean-match-v2.contract.test.mjs`

## 上线前隔离诊断（不开放用户匹配）

- `/api/match-next/status` 继续只报告状态，不泄露 DeepSeek Key。
- **生产环境**：没有通过真实岗位验收前，`HHBA_MATCH_CLEAN_V2_ENABLED` 必须保持关闭；同时 `/resume`、`/ocr`、`/provider-check` 都不能通过预览开关旁路。
- **Cloudflare Pages 预览部署域名（`*.hhba-talent.pages.dev`，不是正式域名）**：仅在单独明确设置 `HHBA_PREVIEW_AI_DIAG_ENABLED=1`，已有后端服务、API Secret、D1 登录会话均有效，且请求携带候选人有效登录 Bearer Token 时，`GET /api/match-next/provider-check` 才调用真实 Balance / Search / Responses JSON / Fetch API。
- 该探针只发送预设公开测试内容，不读取、不发送任何简历，不创建岗位推荐或历史记录，也不开放 `POST /resume`。
- 探针返回 READY **只证明四项基础服务这一次能调用成功**，不能替代多份模拟简历、真实企业 JD 和 Word 优化的端到端人工验收。
- 提交 CI 使用脱敏的合成简历模拟整个 HTTP 路由及证据保存，不能冒充真实供应商联调通过。预览环境未授权或未配置该开关时，探针仍关闭。

## 中国大陆岗位实测（预览合成简历）

- 在 Pages 预览环境 `HHBA_PREVIEW_AI_DIAG_ENABLED=1`，且已登录候选人自愿点击后，`POST /api/match-next/synthetic-check` 使用**服务端固定的虚构汽车区域运营简历**运行与正式匹配相同的：简历原文识别 → Search → Fetch → 具体职位原文证据 → 岗位评分 → 完整 JD 独立核验。
- 该接口接受的请求仅为 `{"consent":true,"scenario":"automotive_operations_v1"}`，拒绝其它字段；不读取当前登录人的简历、简历库、原文件，也不向匹配历史写入测试结果；JD 独立归档只进入隔离的预览 D1/R2。
- 强制验证中国大陆、企业职位来源、原文证据、链接、可信分数，结果列出公司、岗位、城市、官网来源以及完整 JD 核验状态，另展示 Search/Fetch 失败次数。目标 10 条，不到 10 条**如实呈现不足**，不能伪装通过。
- 预检 API 与合成简历验收是不同门槛：前者只检验 DeepSeek 工具与模型健康；后者真实调用岗位搜索流程但使用虚构简历，不能代表任意用户画像的匹配效果。两者均不开放正式 `POST /resume`。
- 真实供应商调用须由已登录候选人自主点击。CI 使用伪造供应商响应测试安全隔离与合同一致性，**不能冒充线上岗位实测结果**。

## 上线门槛

**默认关闭新求职匹配服务。** 仅当安全的真实岗位验收满足要求，才在 Cloudflare 配置 `HHBA_MATCH_CLEAN_V2_ENABLED=1`，将新版正式开放。新引擎尚未经过真实 DeepSeek 生产 Search/Fetch + 登录简历端到端测试，不能宣称已达到 10 个真实职位或已恢复全部 Word 优化的 JD 证据。

放行前需确认：

- [ ] 至少多份不同专业/行业的脱敏简历（不能只针对开发者履历），上海与其他国内意向城市均覆盖。
- [ ] 真实 DeepSeek Key 与实际生产权限/预算，Search、Fetch、Responses 分别记录成功和失败。
- [ ] 每份简历实际找到可打开的公司单岗位详情，禁止 Greenhouse/Lever、第三方招聘平台、校园就业网、公司首页。
- [ ] 任职要求、实际工作城市、个人经历引用逐项正确，不得伪造评分或“在招”状态。
- [ ] 统计真实职位召回量、完整 JD 取得率、官方入口可用率、延迟、错误率，并对每次 0 岗位提供可定位的阶段。
- [ ] 既有 OCR、私有简历库、历史记录、Word 优化前后端真实验收不回归。
- [ ] 实测合格后再开启 V2；之后逐个删除无其他消费者的旧模块和过时测试，而不是直接删除共享数据。

## 纪律

代码测试通过不等于用户求职任务成功。不得在没有真实生产证据时宣布“全面修复”“每次 10 个岗位”或要求用户反复承担测试员职责。
