# HHBA DeepSeek V8：第七至第九轮真实联网验收报告

日期：2026-11-08。状态：**数据及费用链路通过；官方职位召回验收不通过；禁止正式上线**。

## 1. 范围与安全限制

- 试验使用合成角色“内容运营”，不含真实用户简历和联系方式；DeepSeek V4 Pro Responses + 公开 Search/Fetch。
- 每次强制预算 **最多 4 模型 / 8 Search / 20 Fetch**；不使用企业非公开招聘 API。
- 仅允许经真实职位正文、具体大陆城市、企业自有网站身份或公司官网反向指向第三方专属招聘入口、明确资格条件、有效投递入口多重核对的职位进入推荐。
- Search 摘要/站外门户职位列表不构成已证实岗位；模型不得猜测缺失工作地点和雇主身份。
- 调用价格均系按 API 使用量及公开快照推算，**并非官方账单**。

## 3. 定位到的两个实际瓶颈

### 3.1 候选发现以招聘门户和就业平台为主
第八轮实际发现 `adquan.com`、`quanzhi.com`、`campus.niuqizp.com`、`ncss.cn`、`zrc-sme.chinasme.cn` 等来源，不是具体招聘企业自有官网。第九轮继续出现 `nmbys.cn`、`risfond.com`、`gzrc.com.cn`、`yingjiesheng.com` 等渠道；它们不能独立证明雇主官方身份。

这些站点已经被加入有界的**招聘门户排除规则**，避免将其页面作为企业自有的单岗证据；这不是维护企业名录或要求企业开放 API。注意不要靠增加硬编码雇主白名单解决此问题。

### 3.2 部分真正企业招聘页公开 Fetch 文本不足
第九轮 `https://careers.tencent.com/jobdesc.html?postId=2094968965272092672` 被抓取后没有解析到**可引用的工作城市**；苏宁 `careers.suning.cn` 的候选页被识别为招聘已关闭。对没有明确页面证据的职位继续拒绝，不因其域名真实而放行。

需要判断页面是否由 JS 动态加载岗位字段，或 Fetch 返回的是错误/占位/缺省正文。**不要将搜索摘要中的城市、企业总部地址或模型推断当成工作地点。**

## 5. 结论与下阶段

**不要合并 PR #299，不开启 hhba.work AI/收费开关。** 当前 PR #299 仍为 Draft，其基底为 V7 开发分支，未经用户验收不会合并 main。

下一阶段应优先：
1. **从真实企业官网出发检索**：通过公开搜索结果中的公司招聘域，发现单岗详情；对第三方招聘站/公共就业平台做来源类型判定，不浪费 Fetch。保持对全国任意企业开放、不维护固定企业 API。
2. **解决真正公司官方详情动态内容**：对经合法公开访问的页面尝试原始 HTML 的 JobPosting JSON-LD、公开服务端渲染、正常浏览器渲染（若网站允许）和明确的岗位字段映射；对登录限制、验证码、反爬限制不得绕过。
3. **双证据认证与资格**：企业官网链接或确切招聘板反向证明，单职位正文中的大陆工作城市、学历、经验、资格及投递入口均须具备；状态不明拒绝。
4. **再做成本受控的真值验收**：至少验证可独立人工复核的几个真实岗位及其完整证据与负例；以可信岗位数、官网身份准确率、Fetch 解析率、拒绝误报率及每个合格职位成本评估，而不是以 URL 候选数量评估。

本轮真实付费研究已经表明当前方案“能搜索、能调用”但尚不能稳定产出官方合格职位。此报告专门保留这个差异。
