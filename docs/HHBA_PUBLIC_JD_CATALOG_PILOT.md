# Public JD catalog pilot

This is an opt-in background collector, not a replacement for V4 live research. Existing industry-hall URLs are merely seeds, and only independently retrieved, complete same-origin JobPosting documents matching the source employer are archived. Robots restrictions and cross-origin links are skipped. No model calls or applicant data.

Deployment: existing standalone JD lifecycle worker (`apps/web/ops/jd-lifecycle-cron-worker.mjs`), with its existing public D1 and R2 bindings. Preserve the existing daily maintenance trigger; add `*/15 * * * *` for catalog collection. Set `HHBA_PUBLIC_JD_CATALOG_COLLECT=1` only after a pilot review of the worker and bindings. Set `HHBA_PUBLIC_JD_CATALOG_READ=1` on Pages only after the first successful catalog snapshot. Both switches default off. No paid resources requested.

Each invocation tries up to four employer entries, with a bounded public read batch and a rotating D1 offset. A single small public snapshot stores up to 2,000 recent job metadata records, not private data or full text. The original JD archive stores verified text. Strong ETag-enabled pages also populate the existing conditional cache keyed by exact company, title and location, enabling foreground origin revalidation with 304 and reuse of independently read JD text. Hints expire after 24 hours and the foreground still independently checks sources and scores each job. The sample size and static-source restrictions apply only to this optional prewarming path, never to live AI research. This is a pilot, not a complete census; dynamic, cross-origin and unfamiliar employers remain available to live search.

Operational acceptance: confirm scheduled trigger, bindings, log counts, actual employer success rates, snapshot freshness, no resource-limit failures, and real 500-to-50 task latency. Disable either switch independently for rollback. No deletion of previously archived JD documents.
