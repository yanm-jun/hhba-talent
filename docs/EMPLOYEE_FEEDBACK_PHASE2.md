# HHBA「我要招人」模块 06：员工反馈与隐私保护（2026-10-25）

**当前状态：隔离研发分支、前后端与数据库代码存在、真实员工入口关闭。**
上一阶段企业证据已完成开发环境/CI 的审核链路验证，但真实认证后端、文件安全扫描和持久安全存储尚未接生产。

## 本模块目标
在 HHBA 招聘体系中建立**核验员工身份、隔离敏感身份和评价内容、限制重复提交、拒绝小样本公开**的初始能力，让「员工善待值」未来有可信的员工视角输入；不能把个体主观评分直接变成法律违规结论或直接影响帮扶资格。

## 交付范围
- `infra/migrations/20261025_employee_feedback.sql`：资格票据表与员工反馈表物理分离。反馈表不存在员工 ID、资格凭据、精确时间、评论、工资、部门、位置和联系方式字段。
- `apps/api/feedback_domain.py`：员工季度匿名化键（HMAC，部署级高强度密钥）、随机资格票、票据有效期 ≤24 小时且不跨季度、5 项 1–5 分严格校验，**10 人最小样本 + 季度完结后才可公开**汇总。
- `apps/api/feedback_store.py`：每一位经独立核验的员工每企业/每季度最多一份；票据并发事务一次性核销，不能转让给其他员工使用；安全聚合对外不泄露原始数据。
- `apps/api/feedback_routes.py`：员工票据申请、反馈提交、公开聚合路由工厂，必须注入已核实的 `resolve_employee` 和 `verify_employment`；**不自动安装进目前只有 /healthz 的 apps/api/main.py**。POST 必须在部署集成时使用现有真实会话、CSRF、限流。
- `apps/web/src/pages/EmployeeFeedbackPage.tsx`：员工视角问卷，有明确知情说明，不能让员工在没核验身份或没选全 5 项时提交。静态 Pages 的功能开关保持禁用。

## 核验人、员工、企业之间的权限边界
- 企业 HR/老板**不能**查看单条反馈、员工身份、凭据发放清单、真实提交时间，也不能从后台给自己公司的员工生成票据。
- 核验员工在职关系须由**独立**可信的服务端关系证明流程处理；不能使用招聘企业自己上传的名单作为唯一证据。
- 同一员工不同季度的个人资格指纹使用按组织/季度分域的 HMAC，泄露数据库不应直接还原员工 UUID；HMAC 秘钥必须在后端 Secret Manager 中，**不得进代码/静态文件/前端构建产物**。
- 工单和评分记录没有可 JOIN 的身份键，但这属于**去标识化**，不承诺绝对匿名。数据库管理员、请求日志、调用时序仍可能被关联，部署时需分角色数据库权限、敏感 HTTP 请求体不记录、单独加密、严控查看、限制保留期限、定期隐私测试。
- 反馈期为 UTC 自然季度。没到下一季度，或有效反馈数少于 10，公众和企业都统一看到 `not_public`，**不公开具体样本数**、时间、岗位、部门和自由文本。
- 只存 5 个固定题项：工资体验、社会保障体验、工时休息、管理尊重、职业成长。禁止评论输入、防止上传个人身份信息。
- 为避免暴露员工，停止对外提供“谁提交了反馈”“本周新增几条反馈”等仪表数据；管理员也只有必要时的受限系统级诊断能力。

## 上线前必须补齐
1. 确认既有真实招聘/人才后端位置及数据库，**接入可信员工账号会话/CSRF，并增加独立在职关系核验机制**；同时明确如何处理临时工/实习生/离职员工等条件。
2. 为`/employee-feedback`增加服务端限流、抗恶意请求、系统防滥用，并对资格 token 及原始 HTTP 请求体彻底停止日志收集。
3. 数据库不同读写职责拆角色权限，并配置加密存储、备份、审计、保留与清除策略；完成正式隐私告知、员工意见及相关法律合规评估。
4. 考虑在提交前引入随机延迟/安全入库队列以减轻时序关联、季度冻结聚合。对边缘群体采取更高阈值或完全拒绝公开。
5. 个人删除/撤回需要在提交前说明能力边界。无身份关联的已聚合结果无法可靠定位某份个人评价；需要经过隐私评估决定正式流程。
6. 独立核验服务没上线前，`VITE_HHBA_EMPLOYEE_FEEDBACK_API_ENABLED` 必须是 `0`。禁止使用 Browser header、demo 密码、用户自己填员工身份进行放行。
7. 待模块 07（评分规则与证据质量）、模块 08（异议申诉）到位且完成抽样反刷分和误差评估后，才能考虑把汇总作为“员工善待值”输入，更不得直接据此决定客户帮扶。
8. 当前不提供实际反馈、员工身份核验或正式匿名承诺；页面是交互结构预览。
