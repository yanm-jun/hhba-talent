# HHBA 视觉优先原件编辑｜P1 实现与验收（2026-11-20）

> 独立 PR #405 的增量研发记录。当前为 Preview-only / Draft，不应宣传为“任意 PDF/Word 可无损原位编辑”。

## 产品方向

用户上传的是**原始简历**。平台负责在后台理解页面布局，前端只展示文件与必要的修改控件，不展示模型、OCR、解析比例等技术流水线。原件与编辑副本必须分离。

## 本次已落地

1. 私人简历库上传后直接显示原文件预览；已有文件新增「查看」入口。PDF 通过固定版本的 PDF.js 在浏览器本地把**实际保存的原始 PDF**绘制到 canvas，不从提取文本重新排版；只通过账户授权的原有附件下载 API 获取 bytes，不使用公开 R2 链接。
2. DOCX 当前仅展示本地提取的文字校对预览，并明确声明不能保证原始字体、表格、双栏样式；禁止把该视图称作 Word 原件高保真渲染。
3. 新增服务器接口 `/api/resume-layout`。仅当候选人登录、用户主动发送 `consent_ai_vision:true`、源文件 ID 属于该账户、Preview/Production 独立功能开关已开启、数据库与提供商已配置时，才从私有 R2 读取原 PDF。服务器以 OpenAI Responses API 的 PDF `input_file` 高细节模式进行多模态理解，向模型请求页面区域、文本、分栏和 0–1000 相对坐标；未持有外部可公开访问的文档 URL。
4. 标准化结果含页面、段落类型、候选文字、相对框、置信度和“待校验”标记；所有来源模型的坐标均视为**未验证**，绝不直接授权写回 PDF。
5. 已核验的模型结果缓存在同一私有 R2 桶，按原件存储 key + 原件 SHA-256 隔离。候选人再次确认使用同份简历时复用缓存，不重复调用模型。删除原件时一起清理对应缓存。
6. 新增 D1 独立每日调用尝试账本 `0025_resume_visual_attempts.sql`；单账户每日最多两次未缓存尝试（模型失败也计入），规避无限重试付费。**只在 Preview D1** 执行了增量迁移并确认表、索引存在；生产 D1 未改动。
7. 浏览器 QA 使用纯合成 PDF 验证 PDF.js 可绘制原始页面（含中文网页界面），同时保持原有 AI 原位建议、版本保存、A4 PDF/Word 导出回归。服务器契约测试验证了显式授权、相同源站、候选人身份、文件属主、私有缓存和请求上限。

## 默认关闭与接入边界

- `HHBA_RESUME_VISION_ENABLED=1`：独立开关，**目前没有开启**。
- `HHBA_AI_OPENAI_API_KEY`：服务端密钥，必须在 Cloudflare 的加密环境绑定中配置，禁止提交代码或在浏览器泄露。
- `HHBA_RESUME_VISION_MODEL`：可选，默认 `gpt-4.1-mini`；选择时应再次核实当前价格、视觉 PDF 支持及 API 权限。
- Preview 页面已绑定独立 R2 和隔离 D1；**没有发送任何真实候选人 PDF 给外部视觉模型**。
- API 使用 OpenAI PDF 内嵌页面视觉输入；当前 DeepSeek 的图像接口不等于 DOCX 原版式渲染器，不能无转换直接兑现同样的 PDF/Word 保真效果。
- 视觉模型输入会包含未必能完全脱敏的文件原件，因此必须独立征得清晰的第三方模型共享授权。响应使用 `store:false`，但仍要依据正式隐私说明、服务商政策和合法跨境传输安排核实完整数据处理链路。
- 模型生成的结构化缓存可能含个人信息，必须与源文件同级保密、按删除操作清理。

## 明确尚未实现

- **视觉识别已接入原件页的段落定位、人工修改及私有草稿保存。** 但尚未接入整个岗位定向优化后的最终导出链路；服务开关未开启，尚未实测真实模型完整响应，不能宣称线上可用。
- Word 原件像素级预览需要后端可信 DOCX→页面转换器（自托管优先），不应借助公开 Office 在线预览 URL 泄露私有简历。
- 视觉框仍需与原始 PDF.js 文本对象/坐标进行一致性校验，才允许把用户确认的修改关联到具体段落；识别低置信或多栏错序时必须阻止自动替换。
- 原 PDF 中替换文字需要真实排版和重流引擎；当前版本仅有基于结构化文本的 PDF/DOCX 标准版导出，不保证保持复杂原始设计。不能把 canvas 上覆盖文字视为已修改原文件。
- 真实登录→R2 上传→外部视觉服务→区域校验→原位修改→原样导出 PDF/Word 的端到端闭环尚未完成。

## P7｜Word 原版式“必须保留”硬门槛（2026-11-20）

用户已将“必须保留原文件样式”设为严格产品要求。这意味着**不再允许**将上传的 Word 抽取成普通文字、重新生成一个 HHBA Word 模板后，称其为“保留原版式”；遇到无法保证的文件，必须拒绝原样式编辑/导出，并继续保留原件。

### 本轮实际实现

- `src/services/resumeDocxPreserve.mjs` 提供严格 DOCX 原件局部修改：读取真实 ZIP 中央目录、对 `word/document.xml` 内唯一可确认的 `w:t` 进行最小范围的 XML 转义替换，重新构建该 XML 的 CRC/ZIP 目录；所有**其他 ZIP 成员的原始压缩数据逐字节不变**，保留原有字体样式、页眉页脚、表格、图片数据、关系文件与其他原件组件。
- 对跨 Run 拆分的句子、重复原文、无法确定的节点、改写内容明显更长、不支持的 ZIP、宏文件均**拒绝**，绝不重做另一个样式的 Word。支持常见 ZIP Store 和 Deflate 压缩的 DOCX 正文。
- `prepareVerifiedOriginalDocxExport` 为未来唯一允许接入面向用户的“下载 Word”的生产级入口：它要求可信 Word 页面渲染器对原始文档与修改文档作页面视觉保真比对；如果未接入渲染器、渲染失败、页面移动或缺失有效验证数据，则拒绝 Word 导出。底层文件保留并不等于任意文字修改后的页面保真。
- `scripts/word-layout-preservation.qa.py` 使用受控的 LibreOffice + PDF 渲染，将修改前后逐页转为图片。核查：页数/页面尺寸一致、PDF 提取的原文已替换、新文可见、视觉差异被限制在**一处很小的文字改写区域**，其余页面保持不变。文件仅存于系统临时目录，检查结束清理，不向其他模型上传。
- `.github/workflows/hhba-word-original-layout-qa.yml` 为 Word 单独增加真实渲染 QA，合成样本依次通过 ZIP 逐字节校验、渲染页面视觉保真。保留最简用户交互，页面不暴露 ZIP、XML、Word 结构等概念。

### 独立双重验收

- CI 通过两个压缩方式（ZIP store / deflate）的合成 Word 文件，以及包含表格、紫色加粗文字、页眉、页脚、图片资源的 OOXML 保留测试。
- 将 CI 产生的 `original-preserved-layout.docx` 与 `edited-preserved-layout.docx` 下载到隔离环境，并使用官方 DOCX 渲染流程输出 1 页 PNG。两份页面都是相同宽高；实际页面所有不同像素只在目标文字区域，**区域外差异 0 像素**。这只证明该测试样本，不代表任意复杂 Word 文件均可用。

### 上线前仍需开发

1. 将可信私有 Word 渲染器安全地接入真正的业务后端；Cloudflare Pages 本身不提供完整 Word 版面渲染环境，不能在没有视觉验证的情况下解锁 Word 导出。
2. 通过实际 DOCX 原样式渲染，让前端在原文件的真实页面上修改，而不是展示文本重排；前端只出现「修改」「保存」「导出 Word」等必要操作。
3. 验证多栏、跨页、嵌套表格、文本框、图片、中文混排、多字体、页眉页脚等真实简历。无法通过保真检查的仍必须拒绝、不得降级重排。
4. 真实授权会话上传→私有原件→后端渲染→真实视觉定位→修改→保真验证→最终 Word/PDF 双导出；正式站未更新，PR 保持 Draft。

**结论**：本轮解决的是 Word 原件结构的“局部修改和强制验收门槛”，不是任意 Word 的完整上线闭环。用户的绝对要求在产品行为中落实为严格拒绝不保真的导出，而不是无条件承诺任何格式都能正确处理。

## P8｜用户原始 Word 页面预览与保真 Word 导出链路（2026-11-20）

### 产品规则

**原样式必须保留**：有足够证据才能按原样式导出；无法验证则保留原件，绝不重新套用 HHBA 模板伪称原版式。前端只显示「修改」「保存」「下载 Word」等操作，技术名词留在服务端。

### 新增能力（Draft / Preview-only）

1. `services/word-renderer/` 新建单独的私有服务，基于 LibreOffice 在隔离临时目录打开 DOCX，输出用于预览的 PDF 页面；服务只接受后台 Bearer 密钥（至少 32 位）认证，禁止公开下载源文件。限制 3 MB 输入、20 页渲染、并发处理数，拒绝外部资源关系、字段指令、宏、Zip 炸弹等危险内容，不保存客户原件到磁盘以外的持久空间，使用后清理。镜像以非 root 账户运行。
2. `functions/_lib/private-word-service.js` 与 `functions/api/resume-word.js`：与真实候选人会话、私有 R2、源文件 SHA、日调用记录绑定。Word 的唯一定位原文由内部 DOCX 节点提供；后端 `prepareVerifiedOriginalDocxExport` 先在原包内安全改字，再把原文件和修改件发给受信任的私有文档服务进行**页面渲染差异校验**，通过后才将独立 DOCX 和 PDF 预览缓存到当前用户私有 R2。
3. `OriginalWordViewer.tsx`：与原始 PDF 分开，直接显示 Word 原始页面渲染结果，用户点击确认的段落后贴着原文修改。显示 Siri 四边柔光；成功保存后直接显示已修改的真实 Word 页面，并开放「下载 Word」。为防止保存版本在多次改写中出现错配，本阶段仅支持**从原件产生一份验证过的单处改写副本**；需要继续修改时，下载这份文件重新上传。尚不宣称任意多处同时改写。
4. `resumeWordAnchors.mjs`：原 Word 包内唯一 `w:t` 文本节点与原件渲染 PDF 中唯一同文本位置相互交叉核验。分割 Run、重复内容、跨页重复和不明确坐标不可编辑；复杂 Word 格式依然可以查看，不可验证的部分不得覆盖。
5. `d1/0026_resume_word_attempts.sql` 仅在 **Preview D1** `hhba-pnvs-auth-staging-20261103` 完成表和索引迁移，独立给 Word 原页渲染和保真验证设置日调用次数。生产 D1 未迁移。
6. 原简历删除时一并清理 Word 原始预览、已验证的 Word 副本、修改后的页面预览和缓存状态；所有响应 `no-store`，不产生公开 R2 简历地址。
7. 有真实 Chromium 合成 Word 页面编辑验收：1100px 和 390px 设备中原 Word PDF 页面定位→打开 Siri 流光浮层→确认→保存→重开已修改页面→下载 Word。另在 Node 和独立 Python 服务测试中验证权限、私有传输、拒绝未授权请求、拒绝排版变化、删除清理和真正的 DOCX→PDF / 前后像素保真。无真实用户或真实个人信息。

### 部署与隐私硬边界

- **当前 Cloudflare Preview 没有配置 `HHBA_WORD_RENDER_ENDPOINT` 和 `HHBA_WORD_RENDER_SHARED_SECRET`，开关 `HHBA_WORD_RENDER_ENABLED` 默认关闭；因此真实站点上仍只能显示 Word 文字预览，这一新功能尚未开放。**
- 必须先部署**受控的私有渲染服务**（`services/word-renderer/Dockerfile` 从项目根目录构建），为服务器端配置匹配且安全保存的专用密钥，并在隔离 Preview 用授权文件进行端到端验证。禁止未经隐私审核将真实简历传给不受控的公有 Office 在线预览网站。
- 即使源文件全部样式 XML 未改，文字宽度变化也可能改变分页。系统以真实页面渲染和局部差异检查作导出前置条件，不通过不得下载；LibreOffice 渲染结果与其他 Office 客户端可能有环境差异，需在正式发布前完成更多字体、操作系统和真实简历对照验证。
- 单个测试样本通过保真验收**不代表任何 Word 文件都能原样式编辑**。复杂文本框、多栏、嵌套表格、跨行 Run、跨页改写仍可能拒绝。后续继续完善文档渲染端到端校验与 AI 建议定位，不能放弃原样式约束。
- 生产主站 `hhba.work`、生产 D1 不变，当前仍为 Draft PR #405。

## P9｜原位修改与补充文字的 Siri 彩虹流光（2026-11-20）

### 视觉产品原则

用户要求：**不是只给弹窗加渐变边框，而是让简历原页面上已经确认修改、补充的文字本身出现 Siri 式彩虹流光。** 手机与电脑保持同一方案；未修改的原文不得一同着色，界面不额外堆技术术语。

### 本轮已实现

1. `siri-edge.css` 新增公共 `hhba-resume-siri-letters` 与 `hhba-original-resume-siri-ink`：青蓝、靛蓝、紫、粉、暖橙连续流动，缓慢柔和。系统开启减少动态效果时动画停止并保持静态渐变。**彩虹色是编辑预览状态，不进入任何 PDF 或 DOCX 的导出文件。**
2. PDF 原始页面上，只有已保存且通过原生文本映射、背景与长度安全验证的替换文字才以 Siri 渐变文字显示；未确认建议和原始文件文字不会误着色。保存和撤销沿用此前的私有 R2 版本机制。
3. Word 原始页面是来自私有文档服务渲染的真实 PDF，不能靠重新输入一层猜测字体造成走样。新增 `resumeSiriInk.mjs`：从**已经保存、重新渲染且版式验证通过**的 Word 页面中，使用 PDF.js 抽取真实文字和像素，验证修改文字在整份文档中唯一，再从实际笔画制作透明遮罩。彩虹色只作用于对应文字的像素，不覆盖其他页面、不重排字体或表格。页面为复杂背景、无法可靠定位、文字重复或提取失败时自动不着色，不以错误颜色污染原件。
4. 岗位 AI 修改/补充编辑器中的已接受内容，通过 `resumeChangedText.mjs` 提取原文与确认后的差异，只对新增或替换字符施加彩虹色；未改动部分保持普通文字颜色；撤销后恢复原稿并移除高亮。
5. Node 测试覆盖 Unicode 编辑文本的新增、替换、删除、未变更边界，以及 Word 真实笔画遮罩、背景安全检查；Chromium 在电脑 1100px、手机 390px 均断言 Word/PDF 的渐变和动画、Word 的 PNG 像素遮罩、系统减少动画时停止，以及 AI 已接受建议的填充高亮与撤销移除。
6. 操作不引入额外的前端名称或设置面板；不需要用户单独开启彩虹色选项。

### 当前边界

- 彩虹色仅用于正在编辑或回看修改的**页面视觉提示**，导出的正式 PDF / Word 使用原文件文字样式；这是为了继续满足“必须保留原排版/原文件”的要求。
- 仅已核实位置、已确认修改且实际能够安全显示的范围会着色；保存但未能安全放入原位置的 PDF 长文案不强行覆盖，复杂 Word 也不以重新套模板的方式伪造修改。
- Word 私有渲染器当前仍没有在正式 Preview 线上接入机密凭据；上述浏览器截图使用虚构文件与模拟响应，原版式 Word 服务端测试则使用真实虚构 DOCX 页面渲染。尚不可称完整线上闭环。
