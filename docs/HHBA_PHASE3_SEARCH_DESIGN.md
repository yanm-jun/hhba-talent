# Phase 3 搜索设计

## 字段与来源

| 字段 | 来源 | 可检索前提 |
|---|---|---|
| 展示名称、能力标题、技能、服务 | 个人确认的 profile content | confirmed + enterprise_search |
| 经历/教育概括、行业、地区、合作方式 | 个人确认的结构化明细 | confirmed + enterprise_search + 字段可见性 |
| 原始简历、原文证据、联系方式 | 私密文件/数据 | 永不进入搜索投影 |

## 查询整理

Phase 3A 使用本地、确定性规则：提取显式技能、地区、行业、合作方式、出差/远程等；不确定字段保留“待确认”，不能编造。HR 在发送检索前确认/移除条件。未来引入模型必须先完成数据处理审批，且不发送真实简历给外部供应商。

## 检索与排序

1. 过滤：组织已审核、个人授权、confirmed、字段可见性、结构化条件。
2. PostgreSQL FTS：中文策略需基准测试（例如 simple + 自定义分词方案），MVP 不假设数据库天然理解中文语义。
3. 排序：精确结构化匹配优先；文本命中其次；结果返回可解释的“匹配依据”字段，不返回不透明总分。
4. 空结果：说明没有授权且符合条件的档案；可建议放宽已确认条件，但不泄露未授权数量。
5. 低置信度：明确显示条件覆盖不完整，提供继续调整而非“精准匹配”。

## pgvector 启用门槛

仅当合成评测集显示 FTS 对同义能力检索明显不足、且授权过滤/撤销同步压测通过后引入。候选 embedding 仅从可检索投影生成，并带 `profile_version`、模型版本、授权状态。推荐先使用不下载模型的占位接口；本地 embedding 模型的名称、许可证、下载量、CPU/RAM、缓存路径和离线测试须另行批准。

## 反枚举与限流

按组织、成员和 IP 三层限流；最小查询长度、分页上限、结果数上限、重复查询退避；禁止按姓名/ID 批量探测。审计仅记录条件摘要哈希和命中数量区间，不记录完整敏感查询文本。
