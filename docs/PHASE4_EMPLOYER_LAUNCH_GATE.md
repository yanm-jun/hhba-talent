# HHBA Phase 4 — 企业端上线关口

本文件是当前代码的真实状态说明，不代表企业 API 已部署。

## 现在已经做好的代码

- 分身份注册：求职者不能冒充招聘经办人创建企业；组织与招聘人员认证独立
- 主体证照、经办人关系和企业招聘授权材料上传；管理员对材料做**人工核验**，不能由前端自动宣布认证通过
- 企业招聘职位有独立 `employer_postings` 数据表、数据库迁移、私密草稿、编辑、提交、独立管理员审核、拒绝、发布、关闭、到期
- 招聘主体和经办人的认证、成员权限、授权状态或招聘服务开关一旦失效，公开职位接口不再返回该职位
- 候选人搜索只读 `enterprise_search=true` 且已确认的投影，不返回原始简历、联系方式及未经本人授权的数据；撤回同意后即时从搜索结果剔除
- 新前端 `/employer/workspace`、`/admin/recruitment`、`/candidate/employer-jobs`；企业自发布岗位与官方 ATS 职位明确分源显示
- GitHub Pages 白色站没有企业 API 时必须保持只读预览，**不伪造企业、候选人、招聘岗位、审核结果或数据写入**

## 需要后续部署才能真正运行的内容

1. 部署数据库、`apps/api` 与 Alembic 迁移，部署前人工确认迁移 heads、PostgreSQL 用户权限和数据备份；**严禁在实时招聘索引数据库上盲目执行**。
2. 以受控管理员身份配置 `network_recruitment` 服务开关，明确人力资源服务所需的许可/备案及合规责任。不得因前端页面已经写好就擅自开启。
3. 正式上线须有适当的同站身份认证架构：GitHub Pages `yanm-jun.github.io` 和独立 Railway URL **不是同一站点**。当前服务端 Cookie 为 `SameSite=Lax`；仅把 `VITE_API_BASE` 改成 Railway 域名并不能保证跨站登录成立。推荐使用已验证的同站自有域名，或把前后端置于同域可信反向代理下，再验证安全 Cookie、CSRF、精确 CORS 白名单以及移动 Safari。
4. 只有同站登录在生产实测通过后，才在 Pages 或同域站点构建时配置 `VITE_API_BASE` 为有效的 HTTPS `/api/v1` 地址。**不在前端配置私有数据库密码或 DeepSeek Key**。
5. 进行真实但受控的企业/管理员联调：提交合成证照、人工独立审批合成企业、创建职位、提交岗位审核、公开查询、关闭下架、撤销招聘授权立即下架；无需用真实个人简历进行公开测试。
6. 企业端不应使用独立于全站的伪登录数据或假数字；未认证企业仅可保存私密草稿，不能发布，也不能检索人才。
