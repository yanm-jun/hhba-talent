# HHBA 招聘责任机制 Phase 1 — 原系统增量开发与接入边界

本阶段保留现有首页/公开信/招聘市场，以及求职者端“我的申请”、企业端“收到的求职申请”、既有私有管理中心。**不另建后台、不制造岗位、不制作假的申请记录。**

## 已开发内容
1. 现有企业申请面板增加真实责任待办、状态和截止日期读取；原申请状态操作继续保留，“开始审阅”不结束责任。
2. 现有求职者“我的申请”增加服务端认证的申请回应期限；保留撤回和隐私授权。
3. 现有管理员招聘审核页、公开静态管理预览及受保护管理台导航增加“招聘履约管理”，静态预览严格返回未连接；从未展示虚构的企业或回复率。
4. 私有 Postgres 增量表记录站内真实投递的申请 ID、主体、期限、责任人、处理事件。记录审阅中不算履约；拒绝/面试/录用是明确初步处理。事件日志禁止更新或删除。
5. 新增隔离的独立审核员只读接口，排除其本身关联企业；未经独立认证不能查看其他企业招聘数据。
6. 试点规则：企业成功收到站内申请后按中国工作日日历计算 7 个工作日，必须提供完整、经过核验的节假日和调休表版本。

## 接入正式业务服务之前的硬前提
- GitHub Pages 的账号 API 当前关闭，apps/api/main.py 只有健康检查。这些源码和合同测试可验证，但 **并不代表站内真实招聘申请责任已生效**。
- 需在正式后台核查唯一权威的用户、企业、岗位和申请表、UUID 类型、会话权限、组织成员权限、审核员授权；确认所有真实事件能够传送到该模块。
- 数据库迁移 infra/migrations/20261026_recruitment_responsibility.sql 为**待审批脚本**，不会自动执行，也不能视为已部署。
- 申请送达与原站内申请落库之间需要同事务的可靠 outbox；同步成功的事件才调用 record_delivered；状态转移必须由正式业务后端确认后才能调用 record_canonical_transition。不得提供外部 API 让企业自行声称“已审核”。
- 处理期限由 BusinessCalendar 明确的中国节假日、调休和工作日计算；没有经过核验的日历，则不对用户承诺一个看似准确的截止时间。
- 提醒需要真正的通知发送渠道、失败重试、幂等保证及发送成功凭据。只有发送实际成功后才可记录 notification_delivered，当前未部署通知任务。
- 认证、CSRF、速率限制、审计、隐私/删除与合法资质校验必须完整，才可以将独立 router 挂入权威 API。不能使用演示用户、万能密码、浏览器 header 冒充真实账号。
- 完成对公司暂停招聘、负责人离职、取消/撤回申请、纠错申诉、节假日、业务断网、重复事件和跨企业访问的测试，最后才可以开启 VITE_HHBA_RECRUITMENT_RESPONSIBILITY_API_ENABLED=1。该开关与真实账号 API 同时为真时才能工作。

## 本阶段未做的工作
- 企业发邀请后失联的独立流程（第二阶段）
- 对企业自动扣分、处罚、公开排名、付费免除责任（不应自动实施）
- 外部 ATS 官方链接申请的真实状态同步（不可伪造）
- 在实际生产环境运行 DB 迁移、私有会话 API、通知 worker（这些仍是后续接入工作）

## 验收分级
A. 源码已提交：可检查 UI 组件、私有服务模块、数据库增量脚本；
B. CI 验证：必须运行 Node 页面合同测试、TypeScript/Vite 构建、Python 期限与 RBAC 测试；
C. 生产启用：必须提交真会话、真组织、真申请、真回应、真通知记录，并完成权限和隐私复核；否则只能说“开发版已就绪，业务尚未启用”。
